## Strategy

Two categories of uncovered code:

1. **`CompileValidatedDynamicWind` (0%)** -- 90 lines, the single largest gap. This compiles `dynamic-wind` to inline bytecode. It works (tested in `registry/core/prim_dynamic_wind_test.go` at the runtime level), but the machine package tests never exercise it. Add end-to-end tests that compile and run `dynamic-wind` expressions.

2. **Error branches (~25 lines across many functions)** -- These are `if err != nil { return err }` guards for sub-compilation failures, plus a few edge cases (duplicate params, empty bindings guard, unknown type fallback). Most are defensive and hard to trigger through normal Scheme because the validator catches malformed input first.

### What NOT to test

- Error branches that can only fire if a `ValidatedExpr` is malformed (the validator prevents this). Testing these would require constructing invalid `ValidatedExpr` values by hand, which tests implementation details, not behavior. These are legitimately unreachable in normal operation.
- Functions already at 100% (`CompileValidatedDefine`, `emitDefineStore`, `compileBody`, `CompileValidatedQuote`).

## Plan

### 1. `CompileValidatedDynamicWind` -- Full Coverage (0% -> ~100%)

Create `compile_validated_test.go` with tests that compile and execute `dynamic-wind` expressions through the existing test infrastructure (`newTopLevelThunk` + `MachineContext.Run`). These need the full runtime environment since `dynamic-wind` calls thunks.

Tests to add (all as table-driven entries):

| Test | Scheme Expression | Verifies |
|------|-------------------|----------|
| basic dynamic-wind | `(let ((x '())) (dynamic-wind (lambda () (set! x (cons 'in x))) (lambda () (set! x (cons 'body x))) (lambda () (set! x (cons 'out x)))) x)` | before/thunk/after all called in order; result is thunk's return |
| dynamic-wind return value | `(dynamic-wind (lambda () #f) (lambda () 42) (lambda () #f))` | returns thunk's value |
| dynamic-wind with side effects | `(let ((log '())) (dynamic-wind (lambda () (set! log (cons 1 log))) (lambda () (set! log (cons 2 log)) 'result) (lambda () (set! log (cons 3 log)))) log)` | execution order: before=1, thunk=2, after=3 |
| nested dynamic-wind | `(let ((log '())) (dynamic-wind (lambda () (set! log (cons 'a log))) (lambda () (dynamic-wind (lambda () (set! log (cons 'b log))) (lambda () (set! log (cons 'c log)) 'inner) (lambda () (set! log (cons 'd log))))) (lambda () (set! log (cons 'e log)))) log)` | nested before/after ordering |

These tests will exercise the entire bytecode sequence: compile before/thunk/after, PUSH_WIND, POP_WIND, PEEK_K at various depths, multiple SAVE_CONTINUATION/APPLY pairs, and the DROP cleanup.

### 2. `CompileValidatedCaseLambda` -- Hygiene Scopes Branch (74.2% -> ~90%)

The uncovered code at lines 569-590 handles scopes on case-lambda parameters (hygiene for macro-generated case-lambda). This is the `if len(paramScopes) > 0 { ... }` block. This path fires when a `case-lambda` is generated by a macro that introduces parameters with non-empty scope sets.

Test: A `syntax-rules` macro that expands to a `case-lambda` with parameters introduced by the macro. This requires the full runtime (macro expansion + compilation).

```scheme
(define-syntax make-dispatcher
  (syntax-rules ()
    ((_ body1 body2)
     (case-lambda
       ((x) body1)
       ((x y) body2)))))
(define f (make-dispatcher (+ x 1) (+ x y)))
(list (f 10) (f 3 4))
```

## Non-Goals

- Do not aim for 100% on every function. Many uncovered lines are `if err != nil { return err }` after calling `compileValidated` recursively. These error paths require the sub-expression compilation to fail, which in turn requires malformed `ValidatedExpr` nodes that the validator prevents. Testing them means testing against an impossible state.
- Do not refactor production code to make it more testable. The current structure is correct.
- Do not duplicate tests that already exist in `compile_time_continuation_test.go` or `registry/core/`.
